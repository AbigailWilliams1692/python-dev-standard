# ADR-0001 采用分层模块化单体，按业务域切包

> 状态：已采纳｜日期：2026-11-16｜决策者：项目所有者 + 开发 Agent｜关联：`architecture.md` 第 3–4 节

## 背景

项目由一个人主导、多个模型 / Agent 在不同时间接力开发。当前只有会话一个业务域，但预期会扩展到
知识库、计费、工具调用等域。约束条件：

- 部署环境只有一台机器，无容器编排与独立运维投入；
- 每次接力的 Agent 没有历史上下文，结构必须「看目录就能懂」；
- 未来可能拆服务，但拆分成本必须可控。

## 决策

采用**分层模块化单体**：单个部署单元，内部按业务域切包，域内再分四层
（Interface / Application / Domain / Infrastructure），跨域只通过包级 `__all__` 暴露的公共 API 交互。

具体落点：`backend/app/modules/<domain>/` 下固定 `router.py` / `service.py` / `domain.py` /
`ports.py` / `schemas.py`；`core/` 作为共享内核；`infrastructure/` 放适配器。

## 备选方案

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 单文件脚本 | 起步最快 | 第二个域就无法维护；Agent 容易写成 2000 行 | 不采纳 |
| 按技术分层平铺（models / services / routers） | 目录整齐 | 一个业务改动横跨 5 个目录，与「改动局部化」相悖 | 不采纳 |
| 微服务 | 独立伸缩、故障隔离 | 需要网关、服务发现、分布式追踪，当前规模完全是负债 | 不采纳 |
| 模块化单体 + 域内分层 | 改动集中、可单测、将来可按域拆出 | 需要自律维持依赖方向 | **采纳** |

## 后果

- 正面：新增一个业务域 = 复制一个目录；改一个功能只动 1–2 个目录；`domain` 可脱离框架测试。
- 负面：单进程部署，一个域的内存泄漏会拖垮全部；跨域调用仍是进程内调用，边界靠约定而非进程隔离。
- 风险：随着域变多，`core/` 容易膨胀成新的「万能 utils」。触发条件：`core/` 出现业务词汇时，
  说明该下沉到域内或独立内核。

## 验证方式

- `grep -r "fastapi\|pydantic\|httpx" backend/app/modules/*/domain.py` 应无结果。
- 新增业务域的 PR，改动文件应集中在 1–2 个目录（评审时检查 diff 路径分布）。
- 每季度复核一次 `core/` 是否仍只含技术关注点。
