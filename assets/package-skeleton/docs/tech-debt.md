# 技术欠账

> 状态：生效 ｜ 最后核对：2026-11-18 ｜ 对应提交：初始版本

**登记原则**：不为了显得干净而隐藏取舍。每条都要写清「现在的行为 → 会怎么坏 → 什么触发修」。
已解决的要删掉而不是改成「已完成」，这份文件只放仍然开着的账。

| # | 位置 | 现状与风险 | 触发条件 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | `models.py::_VERSION_PATTERN` | 预发布与构建后缀能被解析，但不参与排序，`1.0.0-rc.1` 与 `1.0.0` 比较结果为相等。按语义化版本，`rc.1` 应小于正式版 | 有下游需要区分预发布版本时 | 引入 `prerelease` 字段并实现语义化比较；这会改变 `__eq__` 语义，属主版本变更 |
| 2 | `compat.py` | 只支持「最低版本 + 主版本相同」的判断，不支持 `>=1.2,<2.0` 这类范围表达式 | 下游需要表达带上限的约束时 | 新增 `VersionSpec` 与解析器，保留现有函数作为便捷入口 |
| 3 | 仓库根 | 没有发布流水线，`python -m build` 与 `twine upload` 全靠手工 | 第一次正式发版 | 加 tag 触发的 workflow，用 PyPI Trusted Publishing（OIDC），不存 API token |
| 4 | `pyproject.toml` | `pytest-cov` 已装但没设 `--cov-fail-under`，覆盖率下降不会被 CI 拦住 | 代码量增长到测试开始滞后 | 先设一个略低于当前值的阈值（如 90），只许升不许降 |
| 5 | `pyproject.toml` | `requires-python = ">=3.10"`，未支持 3.9。3.9 缺少 `dataclass(slots=True)` 与部分 `X \| Y` 场景 | 有下游明确要求 3.9 | 去掉 `slots=True` 并改用 `typing.Optional`，会牺牲内存与可读性，需权衡后写 ADR |
| 6 | 全库 | 没有性能基准，`Version.parse()` 的正则开销未量化 | 出现大批量解析场景（如解析数千个包版本） | 加 `pytest-benchmark` 基线，再决定是否需要手写解析器替代正则 |

## 不属于欠账的取舍

以下看起来像问题，其实是刻意设计，改动前先读 `docs/architecture.md` 第 4 节：

- 不依赖 pydantic：库的默认依赖应尽量为空。
- 不配置日志：库不该决定宿主程序的日志设置。
- 不建 `adr/` 目录：决策密度低，`architecture.md` 的决策表足够。
- 不定义 `Protocol`：每种角色只有一个实现，单实现的抽象是纯成本。
